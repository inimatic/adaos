# Проверка и демонстрация Builder

Документ задаёт повторяемую проверку Builder в Web и Telegram. Он не заменяет
автоматические тесты: ожидаемые состояния, ссылки и кнопки нужно сверять с
каноническим workflow, а не только с текстом ответа.

## Полезные команды Builder

Команды чтения и выбора не должны запускать LLM, Codex или Automation:

| Команда | Ожидаемый результат |
| --- | --- |
| `Строитель, что выбрано?` | Текущий Project, его идентификатор и доступные контекстные действия |
| `Строитель, покажи текущий проект` | То же состояние Project без изменения workflow |
| `Строитель, покажи проекты` | Выбранный Builder/Preview, один рабочий Project Builder, текущая Preview-цель и доступные DEV-проекты с кнопками выбора |
| `Строитель, выбери <id>` | Смена рабочего Project Builder без бизнес-перехода и без неявного переключения открытого Preview |
| `Строитель, помощь` | Контекстная справка и ближайшие безопасные действия без LLM/Codex |
| `Строитель, ссылка на Preview` | Точный `proto:`/`active:`/`public:` target и `webspace.open` URL-кнопка с zone, subnet, Webspace, source boundary и ожидаемым сценарием |
| `Показать процесс` | Состояние активного Change, объяснение и допустимые следующие команды |
| `Показать прототип` | Выбор `proto:` Preview для принятой/текущей UI revision |
| `Показать реализацию` | Выбор `active:` Preview текущей Automation, если она существует |
| `Показать публикацию` | Выбор `public:` Preview установленной опубликованной версии, если она существует |
| `Дополнить изменение` | Запрос недостающего текста для текущего Change; само нажатие не придумывает требование |
| `Доработать прототип` | Запрос замечания к Prototype в текущем Change |
| `Уточнить реализацию` | Запрос инструкции к Automation в текущем Change |

После ответа о текущем проекте Builder предлагает только действия, допустимые
в текущем состоянии. В Web это chat controls, в Telegram — inline-кнопки. Если
кнопки недоступны, точная подпись актуальной кнопки является семантически
эквивалентным текстовым fallback. Подпись разрешается только относительно
последнего незавершённого Interaction; свободное нечёткое совпадение не даёт
полномочий и не запускает изменяющую состояние команду.

Ответ `Строитель, покажи проекты` не использует неоднозначный маркер
«активный» и делится на два блока:

- `Контекст`: Builder Webspace, Preview Webspace, рабочий Project Builder и
  текущая Preview-цель (`proto:` / `active:` / `public:`);
- `Проекты`: один отмеченный рабочий Project и остальные доступные DEV-проекты.

Для каждого проекта Builder предлагает `Выбрать <id>`. Выбор меняет рабочий
контекст Builder, но не открытый Preview. Preview меняют только команды
`Показать прототип`, `Показать реализацию` и `Показать публикацию`; команда
`Ссылка на Preview` открывает уже выбранную цель и сама её не выбирает. После
выбора Builder повторно показывает точную identity и ближайшие действия. При
длинном списке rich Web-поиск остаётся основным интерфейсом; Telegram использует
ограниченный список, следующую страницу или deep link.

`Показать процесс`, `Строитель, помощь`, список/выбор проектов и получение
ссылки на Preview являются детерминированными read/navigation-командами. Они
не создают Skill Factory task и не могут отвечать сообщением «Локальный Codex
ещё выполняет предыдущую итерацию». Callback передаётся как typed action, а не
как повторно распознанный пользовательский текст. Повтор одного Telegram
update допускает повтор доставки сохранённого ответа, но не повтор действия.

После нажатия Telegram-кнопки исходное сообщение переходит в состояние
`consumed`: inline-кнопки удаляются, исходный prompt сохраняется, а внизу
появляется `✓ Выбрано: …`. Для выбора Project показываются его title и
стабильный id. Одновременно выполняется `answerCallbackQuery`, поэтому клиент
не должен оставлять индикатор ожидания. Новое сообщение с результатом команды
остаётся отдельным фактом: переписывание presentation подтверждает выбор, но
не подменяет outcome операции. Текстовый fallback не редактирует сообщение
пользователя, поскольку право на изменение даёт только callback к сообщению
самого бота.

Примеры создания и развития:

- `Строитель, создадим приложение «Список покупок»` — создать новый Project.
- `Строитель, добавь …` — добавить требования в текущий Change либо создать
  новый Change, если текущий завершён или запрос явно независим.
- `Строитель, измени …` — сформировать корректирующее Issue/Change.
- `Исправь workflow.json: …` — Automation/Codex lane, а не UI-прототипирование.
- `Переставь кнопки процесса в правую панель` — Prototype lane, потому что это
  визуальная компоновка, а не изменение statechart.

Системные команды Telegram:

| Команда | Назначение |
| --- | --- |
| `/help` | Справка Telegram-маршрутизатора |
| `/list` | Доступные привязки/контексты |
| `/use <alias>` | Выбрать активную привязку |
| `/current` | Показать текущую и default-привязку |
| `@<alias> Строитель, что выбрано?` | Адресовать один запрос контексту, не меняя default |

Telegram не обязан отображать большие деревья файлов, diff или Preview. Для
них допустим deep link/Web view. Но ограничение канала не меняет workflow,
полномочия или бизнес-доступность действия и не позволяет молча удалить
единственный безопасный способ продолжить.

Preview-ссылка является назначением, а не полномочием. Проверка выполняется в
порядке `zone -> auth -> subnet -> Webspace -> workspace/development ->
complete materialization -> scenario/revision`. При расхождении клиент показывает ожидаемое и
текущее состояние и предлагает явный переход либо отмену; само открытие ссылки
не переключает сценарий. В URL используется `intent=webspace.open`; параметр
`mode` не поддерживается. Не выводите `user_code` или `pair_code` в повторно
копируемую ссылку после завершения авторизации.

## Предусловия проверки

1. API сообщает текущий локальный commit/version через `/health/ready`.
2. После `dev skill push` выполнена одна явная активация новой DEV-редакции.
   Загруженный процесс навыка не считается обновлённым только потому, что файлы
   на диске уже изменились.
3. После публикации dev → workspace код `handlers/main.py`, `workflow.json` и
   тесты совпадают; номера DEV и Workspace версий могут идти независимо.
4. Для HTTP-инъекций кириллицы используется UTF-8 либо ASCII JSON с
   `\uXXXX`. Искажённое отображение терминала не считается порчей данных без
   проверки сохранённых Unicode code points.
5. Для проверки можно создать отдельный сценарий. Не используйте публикацию
   рабочего сценария как пробную операцию.

## Проверочная серия

Отправляйте следующий запрос только после терминального результата или явного
`input_required` предыдущего шага. Не повторяйте изменяющую команду после
таймаута: сначала запросите состояние Run.

### 0. Контекст и каналы

В Web и Telegram:

1. `Строитель, покажи проекты`.
2. Проверить блок `Контекст`: точные Builder/Preview Webspaces, ровно один
   рабочий Project Builder и текущая Preview-цель. В списке не должно быть
   второго «активного» Project.
3. Нажать `Выбрать <test-id>` либо отправить `Строитель, выбери <test-id>`.
   При нажатии проверить, что старые кнопки исчезли, а исходное сообщение
   получило строку `✓ Выбрано: <title> (<test-id>)`.
4. Убедиться, что Telegram сообщает новый рабочий Project Builder и отдельно
   называет неизменившуюся Preview-цель.
5. `Строитель, что выбрано?`.
6. `Строитель, помощь`.
7. `Строитель, ссылка на Preview` и открыть URL-кнопку. Проверить точный target
   и парное Preview-space. В URL должны быть `intent=webspace.open`, `zone`,
   `subnet_id`, `webspace_id`, `space_kind=development`, ожидаемый scenario и
   выбранные revision/stage при их наличии; `mode` отсутствует.
8. Открыть ту же ссылку в браузере, где выбрана другая зона или subnet.
   Проверить объяснение расхождения и кнопки явного перехода/отмены. До выбора
   действия Webspace и сценарий не меняются.
9. В том же `dev1-dev` открыть ссылку на другой сценарий. Webspace mismatch
   появляться не должен: клиент показывает только expected/current scenario и
   запрашивает одно решение. После полной materialization overlay закрывается,
   даже если live Yjs transport ещё восстанавливается.
10. Повторно открыть ссылку, когда expected scenario/revision уже текущие.
    Проверить отсутствие overlay и повторной команды переключения. Новая
    вкладка может заново загружать клиент, но это не повторный Preview switch.
11. Повторить ссылку без активной сессии. После входа должен продолжиться тот
    же `webspace.open`, а не просто открыться Desktop по умолчанию.
12. Проверить, что использованный `connect.register` `user_code` удалён из
    адресной строки и не попадает в Copy Link/историю как канонический адрес.
13. `Показать процесс`.
14. Убедиться, что ответы содержат одинаковый Project и только кнопки,
   допустимые в текущем состоянии.
15. Ввести точную подпись одной read-only кнопки текстом и убедиться, что она
    не уходит в Automation/LLM.
16. Проверить журнал: ни один шаг 1–15 не создал Codex/LLM/Automation Run.

История до и после Interaction должна оставаться видимой. Webspace, Telegram
binding и Project focus не обязаны быть глобально одинаковыми; явная
адресация выбирает нужный контекст.

### 1. Проверка состояния без изменений

> Ничего не изменяй. Покажи текущий Project, активный Change, выбранный узел процесса и точный Preview target. Подтверди, что Preview работает в отдельном пространстве.

Ожидается Project identity, отсутствие либо точный `change_id` и `proto:`
Preview в парном DEV Preview-space. Запрос не создаёт Run.

### 2. Создание Change и Prototype

> Я хочу вести список рецептов. Создай один Change и разложи запрос на связанные Issues. На первом экране нужны поиск, фильтр избранного, карточки рецептов и кнопка добавления. Сначала сделай только Prototype на мок-данных. Не запускай Automation до моего согласования интерфейса.

Проверить один Change, несколько Issues, `prototype_first`, mock/fixture data
mode и новую immutable Prototype revision.

### 3. Итерация того же Change

> Уточнение к текущему Change: на широком экране покажи карточки сеткой, на компактном — одной колонкой. На карточке нужны название, категория и признак избранного. Добавь понятное пустое состояние. Не создавай новый Change.

Ожидается новый iteration Run/Prototype revision внутри того же Change.

### 4. Review

> Review текущего Prototype: кнопку добавления сделай основной и назови «Новый рецепт». Поиск размести перед фильтрами. Эти замечания добавь в существующие Issues и покажи обновлённый Prototype.

Дополнительно создать ошибочный Review prompt, удалить/withdraw его до
применения и проверить, что он отсутствует в активном model context, но
сохранился минимальный audit tombstone.

### 5. Передача в Automation

> Мне нравится текущий Prototype. Зафиксируй его как согласованную alpha-версию. Покажи implementation brief, acceptance criteria, исходную ревизию и Issues. После этого передай реализацию встроенному Codex.

Automation должна ссылаться на точную Prototype revision. Согласованный
Prototype не переписывается.

### 6. Прямой функциональный Change

> Добавь локальное сохранение рецептов и тесты. Интерфейс не меняй. Сформируй Change и подготовь Automation, но дождись подтверждения запуска Codex.

Ожидается `automation_direct`; Prototype LLM не запускается.

### 7. Коррекция declarative workflow

> Исправь workflow.json: запрети публикацию без принятого Trial, добавь typed reason code и проверь все состояния. Не изменяй webui.json.

Ожидается Automation/Codex lane, структурная проверка полного
`TransitionDescriptor`, graph diff и отсутствие UI revision. Изменение
definition не активируется отдельно от кода/package generation.

### 8. Асинхронный Automation Run

> Реализуй локальное добавление, редактирование и удаление рецептов, поиск и избранное. Данные должны сохраняться локально, без внешней сети. Используй согласованный Prototype как требование. Запусти тесты, но не создавай Trial автоматически.

Проверить последовательность: accepted → started → progress → при
необходимости input_required/resumed → один terminal outcome. Progress не
равен workflow state, а delivery результата не повторяет Codex/tool.

### 9. Контроль и восстановление

> Покажи состояние текущего Automation Run, выполненные команды, изменённые файлы, тесты и оставшиеся acceptance criteria. Ничего не запускай повторно и не изменяй состояние.

После перезапуска результат и ReplyRoute должны оставаться queryable. Повтор
доставки создаёт DeliveryAttempt, но не новый Run.

### 10. Trial

> Если Automation завершена и acceptance criteria выполнены, подготовь неизменяемый Trial. Покажи точные версии Prototype и Automation, зависимости и результаты проверок. Не публикуй.

### 11. Обратная связь из Trial

> В Trial проверь создание рецепта без названия, переключение избранного и сохранение после перезагрузки. Если обнаружится дефект, добавь Issue в тот же Change и создай отдельный repair Run. Не повторяй уже подтверждённые команды.

### 12. Publication

> Подготовь кандидата Publication из принятого Trial. Покажи состав, версии, доказательства и ожидаемые изменения Workspace. Жди отдельного подтверждения публикации.

Только после проверки:

> Публикацию подтверждаю. Опубликуй принятый кандидат и проверь `public:` Preview и точную Workspace-версию.

Проверить immutable source/package/candidate/release lineage и атомарный
WorkspaceLock. Истиной версии исходника является YAML manifest.

### 13. Негативные проверки

- Нажатие устаревшей кнопки возвращает fresh frame, а не выполняет команду.
- Один и тот же Telegram callback/update, доставленный повторно или через
  relay fallback, создаёт не более одного action dispatch и одного результата.
- После первого callback старое сообщение не содержит активных кнопок;
  повторный token не выполняет действие, даже если клиент прислал его из кэша.
- Сырой либо неизвестный `ia:` token отклоняется с предложением обновить
  состояние и никогда не передаётся в Builder/Automation/LLM как текст.
- Недостающая обязательная capability даёт fallback/deep link/unsupported, но
  не сокращённый набор опасных действий.
- `input_required`, failure и expiry создают escalation; частый progress
  coalesced и не засоряет ленту.
- Quiet hours не скрывают обязательное согласование.
- Архивный Project предлагает Restore, активный — Archive.
- Недоступный `active:` или `public:` Preview объясняет отсутствие источника и
  не подменяется Desktop/другим сценарием.
- Неверный UTF-8 отклоняется до LLM/Codex и не попадает в Clarification history.
